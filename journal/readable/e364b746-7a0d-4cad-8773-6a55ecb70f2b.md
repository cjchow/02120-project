Pick a bug, then find an input where the buggy code and the correct code give **different** answers. If they give the same answer, the test can't tell them apart.

- You need a case where **both** factors are partial, like light = 0.5 and warm = 0.5. Then multiplying gives 0.25, but min gives 0.5.

# What you learned today

**Designing tests**
- A good test case is built to catch a specific bug: pick an input where the buggy code and the correct code give **different** answers.
- Isolate one factor: setting T = T0 makes `warm` = 1, so test 1 checks `light` alone.
- To catch "min or average instead of multiply," both factors must be partial: 0.5 × 0.5 = 0.25, while min and average both give 0.5.
- Test right at a limit, (0.01, 288) → 0, to catch a forgotten "− 0.01" (the bug would give 0.0204).
- Compare decimals with `abs(result - expected) < 1e-9`, not `==`, because computers store decimals slightly inexactly.

**Proving the test works**
- Break the code on purpose (0.50 → 0.05) and check that the test fails, then put it back.
- In the error message (traceback), the **last** line listed is where the failure happened (line 44). Earlier lines show who called it (line 59).
- Python stops at the first failed `assert`, so later tests don't run.

**Verification vs. validation**
- Tests check that the code matches **your design** (verification), even for assumed numbers, because assumed numbers can still have typos.
- Whether the design matches the real world is **validation**: comparing with Bardeen and Brugger on Nov 12.

**Where the assumptions come from**
- 0.50: light saturation is real biology, but 50% is a round-number guess.
- 263 K: cold really does slow enzymes, but −10 °C is a guess and is colder than seawater freezing (~271 K).
- Multiplying: a modeling convention. All three are labeled **assumed**.
